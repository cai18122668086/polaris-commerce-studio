适用主机：香港生产机（8 核 / 15.6 GB 内存 / 4 GB swap），生产站、视频开发栈、mpay、tengli 同机运行。
本文只描述仓库内配置的目标值；**本次没有部署，也没有改动 /opt/polaris 下的任何东西**。

## 2. 连接数预算（PostgreSQL）

每个 uvicorn worker 进程、每个 Celery 子进程各自持有一个 SQLAlchemy 连接池，上限是 `pool_size + max_overflow`。

| 服务 | 进程数 | 池（size+overflow） | 最大连接 |
| --- | ---: | --- | ---: |
| api（本次改为 3 个 uvicorn worker） | 3 | 8+8 | 48 |
| ecommerce-api（新增，单进程） | 1 | 3+2 | 5 |
| detail-api（线上现值） | 1 | 8+8 | 16 |
| replica-api（线上现值） | 1 | 2+1 | 3 |
| video-api（线上现值） | 1 | 3+2 | 5 |
| worker（default，并发 6） | 6 | 2+1 | 18 |
| detail-worker（线上现值，并发 6） | 6 | 3+2 | 30 |
| replica-worker（并发 2） | 2 | 2+1 | 6 |
| editing-worker（本次改为并发 2，按配置建池） | 2 | 3+2 | 10 |
| editing-maintenance | 1 | 3+2 | 5 |
| dispatcher | 1 | 3+2 | 5 |
| crawl-worker / crawl-maintenance（仓库 compose 有） | 2 | 3+2 | 10 |
| supertokens（自带池，默认 10） | 1 | 10 | 10 |
| migrate（一次性） | 1 | 3+2 | 5 |
| **合计** | | | **176** |

`max_connections=200`，减去 `superuser_reserved_connections` 默认 3，剩约 21 个给 psql、备份和临时脚本。
如果把 detail-worker 也调成 2+1，合计降到 164。

说明：

- 改动前的线上配置理论峰值已经约 140，超过 PostgreSQL 18 默认的 100。原因是编辑 worker 和 maintenance 调用了
  `build_database(url)`，没有传池参数，各自用默认的 5+10。本次统一改为 `build_database_for(settings)`。
- 四个 HTTP API 不能都开 3 个 worker × (8+8)：那样仅 API 就要 192 个连接，总数约 310。到那一步应加 PgBouncer
  （transaction 模式），不要继续加大 max_connections。现在只有主 api 开多 worker。
- PostgreSQL 内存估算：shared_buffers 384 MB + 每个后端 3–6 MB 私有内存 × 约 180 + work_mem 峰值，
  合计约 1.0–1.3 GB，放进 1.5 GB 上限。

## 3. 内存 / CPU 预算（上限，单位 MiB / 核）

| 服务 | 旧上限 | 新上限 | 旧 CPU | 新 CPU | 50 用户时的预计峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| postgres | 512 | **1536** | 0.5 | **1.5** | 900–1300 |
| api | 384 | **1536** | 0.5 | **1.5** | 压测实测 759 MiB（50 VU，3 worker） |
| ecommerce-api（新） | – | 768 | – | 0.75 | 200；扫码登录时有 Chromium，约 600 |
| worker | 768 | **1536** | 0.75 | **1.0** | 900–1200 |
| editing-worker | 3072 | 3072 | 1.5 | **2.0** | 两路渲染，未实测，估 1.5–2.5 GB |
| detail-api / replica-api / video-api | 512 / 1024 / 1536 | 不变 | 0.5 / 1 / 1 | 不变 | 250 / 300 / 300 |
| supertokens | 384 | 384 | 0.5 | **1.0** | 登录时的密码哈希在 Core 内完成，CPU 受限 |
| editing-maintenance | 384 | **256** | 0.25 | 0.25 | 实测 91 MiB |
| detail-worker / replica-worker | 2048 / 1024 | 不变 | 0.75 / 1 | 不变 | 700 / 400 |
| redis / minio / dispatcher / frontend / caddy | 112 / 384 / 192 / 384 / 160 | 不变 | | | 合计约 700 |
| **生产合计（上限）** | **12880** | **16464** | **12.0** | **13.25** | **约 8–10 GB** |
| 视频开发栈（上限 / 实际） | 5.5 GB / 0.55 GB | | | | 跑渲染时 1–2 GB |
| mpay + tengli（无上限，实际） | 0.85 GB | | | | 约 1 GB |
| 宿主机开发工具（实际） | 2–3.5 GB | | | | 2–3.5 GB |
| **主机合计预计峰值** | | | | | **约 12–15 GB / 15.6 GB** |

结论：

- 上限总和（16 GB 生产 + 5.5 GB 开发）大于物理内存。这是有意超配：上限是防失控的天花板，不是常驻占用。
  峰值时真正的风险来自 **editing-worker 两路渲染 + 开发栈同时渲染 + 宿主机上的开发工具**。
- 压测和高峰期建议：
  1. 停掉开发栈的 editing-worker，或把它的上限降到 1.5 GB（只改开发栈，不动生产）；
  2. 宿主机上不要同时跑多个 node / workerd 开发服务器；
  3. 盯住 swap：swap 持续高于 1 GB 就把 `POLARIS_EDITING_WORKER_CONCURRENCY` 调回 1。
- CPU 上限合计 12.75 核，主机 8 核，同样是超配。图片和视频类工作大多在等上游 HTTP，真正吃 CPU 的是剪辑渲染
  和 PostgreSQL。两路渲染同时跑时会和数据库抢 CPU，这是首要观察点。

### 压测后的调整（2026-11-25）

- api 上限 1 GiB → 1.5 GiB：压测时 3 个 worker 在 768 MiB 的预发上限下跑到 759 MiB，1 GiB 余量不够。
- 多出的 512 MiB，其中 128 MiB 来自 editing-maintenance（384 → 256 MiB，实测 91 MiB）。
  代价：maintenance 偶尔扫描大批任务时余量变小，超限只会重启这个轮询进程，不影响渲染。
  其余 384 MiB 依靠超配：现在生产上限合计 16.1 GB，主机物理内存 15.6 GB。实际峰值约 8–10 GB。
- supertokens CPU 0.5 → 1.0：50 人在 30 秒内登录，p50 14.6 s / p95 18 s。
  密码校验（哈希）在 SuperTokens Core 内执行，0.5 核把它们排成了队。
- API 侧改动：每个已登录请求原本都要调一次 Core 的 get_user，现在对已验证邮箱的用户缓存 30 秒，
  以减轻高峰时 Core 的负载。

## 4. 并发与准入控制（本次加入）

| 控制 | 默认值 | 环境变量 |
| --- | --- | --- |
| 主 api uvicorn worker 数 | 3 | `POLARIS_API_WORKERS` |
| 主 api 连接池 | 8 + 8，超时 10 s | `POLARIS_API_DATABASE_POOL_SIZE` / `_MAX_OVERFLOW` / `_POOL_TIMEOUT_SECONDS` |
| Celery default worker 每个子进程的连接池 | 2 + 1 | `POLARIS_WORKER_DATABASE_POOL_SIZE` / `_MAX_OVERFLOW` |
| PostgreSQL | 200 连接，shared_buffers 384 MB | `POLARIS_POSTGRES_MAX_CONNECTIONS` / `_SHARED_BUFFERS` / `_EFFECTIVE_CACHE_SIZE` / `_WORK_MEM` |
| 全局上游图片并发（Redis 准入） | 40（原 3000，等于不限） | `POLARIS_IMAGE_GLOBAL_CONCURRENCY` |
| 每个账号同时运行的图片任务 | 3 | `POLARIS_USER_ACTIVE_IMAGE_JOB_LIMIT`（0 = 关闭） |
| 每个用户同时生成的视频 | 1 | `POLARIS_USER_ACTIVE_VIDEO_JOB_LIMIT`（0 = 关闭） |
| 请求限流（固定窗口，Redis 不可用时放行） | 每 IP 1800 次/60 s，每会话 600 次/60 s | `POLARIS_RATE_LIMIT_ENABLED` / `_PER_IP` / `_PER_USER` / `_WINDOW_SECONDS` |
| 限流取客户端 IP：只信任来自这些网段的 X-Forwarded-For；Caddy 用 `header_up X-Forwarded-For {remote_host}` 覆盖该头 | 127.0.0.0/8、10/8、172.16/12、192.168/16 | `POLARIS_RATE_LIMIT_TRUSTED_PROXIES`（JSON 列表），uvicorn 用 `POLARIS_TRUSTED_PROXY_CIDRS` |
| Celery 软超时 | 图片 2400 s，详情 3600 s，复刻 3000 s，剪辑 4200 s，剪辑规划 1800 s | `POLARIS_CELERY_SOFT_TIME_LIMIT_{IMAGE,DETAIL,REPLICA,EDITING,PLANNING}_SECONDS` |
| Celery 硬超时 | 软超时 + 120 s | `POLARIS_CELERY_TIME_LIMIT_GRACE_SECONDS` |
| 剪辑 worker 并发 | 2（范围 1–4） | `POLARIS_EDITING_WORKER_CONCURRENCY`（发布脚本读取） |

超时取值依据：单次上游图片请求的超时是 600 s，最多重试 2 次并带退避，约 1.9 ks；规划阶段另有 analysis 600 s；
剪辑渲染受 `video_editing_subprocess_timeout`（3600 s）约束。图片任务在事件循环里提前 30 s 自行停止，
走 `fail_timed_out` 收尾：未完成的条目标为失败，然后由正常的 `finalize_job` 结算，已交付的计费，未用的预留积分退回。

## 5. 上线前必须知道的事

- 生产实际运行的是发布脚本生成的 `active.compose.private.json`。本仓库的 `deploy/compose.production.yml` 和
  `Caddyfile.production` 要经过发布流程才会生效，detail / replica / video 这几个姊妹服务由各自的 prepare 脚本生成。
- 修改 `shared_buffers` 需要重启 PostgreSQL，要放在维护窗口做。
- 主 api 开多 worker 以后，`/health/metrics` 只反映接到这次请求的那个 worker；会员维护循环每个 worker 各跑一次
  （行锁保证正确，但数据库负载变成 3 倍）。
- 电商扫码登录的状态保存在进程内存里，所以 `/api/ecommerce/*` 由单进程的 `ecommerce-api` 处理。
  不经过 Caddy、直接访问 `api:8000` 的电商调用会落到多 worker 的 api 上，登录状态会对不上。
