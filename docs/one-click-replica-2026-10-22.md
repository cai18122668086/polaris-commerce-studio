# 一键复刻：产品流程与发布说明

用户入口为 `/style-replica`，主导航名称为「一键复刻」。首页用该入口承接原参考图创作卡片的位置，保持六卡布局；原「一键模仿」工作台、任务和菜单入口继续保留。

## 用户流程

1. 上传自己的商品图片。
2. 粘贴淘宝/天猫、1688 或京东商品链接，拉取后按主图、详情图、SKU 图勾选；也可以直接上传风格参考图。
3. 选择「一比一模仿」或「风格复刻」，设置目标平台、语言，填写商品事实和要求。
4. 分析后查看物理拆屏和原生方案，确认实际输出数量后生成；调整要求应返回修改并重新分析。
5. 在当前页面查看、放大和下载已验收图片；刷新、历史记录及任务中心均可返回对应 session。新模式失败时按原方案重新复刻整组，页面明确提示会产生新的 API 用量。

不提供 16 类模块、模型、画质或新模式的任意比例选择。最多选择 20 张参考图：一比一模式按物理拆屏逐屏输出，最多 60 屏；风格模式遵循源路由，独立海报输出单张，套图保留顺序，详情路由按 8–12 屏相邻双屏生成、验收后无缩放切分。实际数量以确认页方案为准，并非固定一张参考对应一张结果。

## 两种原生 Skill

| 模式 | 锁定来源 | 执行与验收 |
| --- | --- | --- |
| 一比一模仿 | 九月合集 `aurora-ecommerce-reference-remix`，v6 | 物理裁切与哈希、九项独立观察、计划及新鲜看图审计、逐屏单次令牌、实图审计、最多一次修复、接受后交付 |
| 风格复刻 | 同一合集 `all-category-style-benchmark-still` | `new` → 路由 → 八类机制分析及实际裁切 → visual passport → 商品事实 → 计划/审计 → 原生生成门禁 → 产物溯源与实图/原创性审计 → 全局验收及交付 |

商品身份和用户事实优先。风格模式提取商业及视觉机制、重建场景与构图，不能保证法律意义的「不侵权」。新文案限制不应擦除用户要求保留的真实商品物理标签。参考原图仅用于分析；风格生成参考使用经过新鲜审查的安全物理裁切。商品图先裁去外部广告抬头，绑定实际商品像素。

完整源协议、Schemas 和 CLI 分别位于 `backend/skill_sources/` 的两个独立目录。原始 ZIP 清单见 `backend/source_manifests/*-20260923-source.json`，运行包哈希见对应 `backend/app/skill_manifests/`；来源补丁另有 `*-polaris-patches.json`，不冒充原始字节。

已记录的源协议兼容补丁：一比一允许真实 `geometry_match=false` 搭配具体差异进入失败/修复；风格套图允许用户明确选择 1/2 张，以及在未生图时修正实际失败的方案并重新审计。未降低商品身份、80% 视觉机制、一次修复或接受后交付门槛。

## 数据与生成

| 来源 | Just One API | 控制台成功请求单价 |
| --- | --- | --- |
| 淘宝/天猫 | `/api/taobao/get-item-detail/v6` | ¥0.25 |
| 1688 | `/api/1688/get-item-detail/v1` | ¥0.10 |
| 京东 | `/api/jd/get-item-detail/v3` | ¥0.40 |

报价查验于 2026-10-21，按供应商控制台账户价格记录；只有成功的数据请求计费，试用请求由供应商执行。同工作区、同平台、同商品在同一北京时间日期内复用成功缓存。勾选多张图片不会重复查询商品 API。

接口依据：[使用说明](https://docs.justoneapi.com/zh/usage)、[淘宝/天猫 V6](https://docs.justoneapi.com/zh/api/taobao-and-tmall/product-details-v6)、[账户控制台](https://dashboard.justoneapi.com/)。

淘宝/天猫以 V6 查询；返回采集失败（业务码 301）或提示商品不存在/已下架时，最多切换一次 V3，并核验返回商品 ID。正常成功、网络异常、凭证/余额/配额错误不触发该备用查询。备用成功沿用当天缓存；V3 的实际费用不沿用 V6 报价。

数据接口不自动回退到自建浏览器。拼多多目前可作为输出目标，来源图片可手动上传；此版本不承诺拼多多链接采集。

2026-11-07 新增 [EveryInfra](https://cn.everyinfra.com/) 商品来源与备用采集。淘宝、天猫、1688、京东继续优先请求 Just One API（淘宝/天猫原有 V6→V3 规则保留）；无有效图片、服务异常或未配置时，最多再请求一次 EveryInfra。原有成功缓存直接复用。1688 主接口缺少详情图时，额外请求一次 EveryInfra 补全详情图，保留原主图和 SKU 图。Amazon 优先使用原有 Just One API 的商品详情接口，读取 product_photos、aplus_images 与 product_variations.photo，失败时回退 EveryInfra；其余新增渠道和速卖通直接使用 EveryInfra；Just One API 的速卖通概览实测只返回文字，不作为已启用 EveryInfra 时的前置付费请求。

来源共 15 个：淘宝、天猫、1688、京东、AliExpress、Amazon、Shopee、TEMU、eBay、Etsy、Walmart、抖音商城、小红书商城、闲鱼、得物。得物使用商品价格概要中的图片，其余使用完整商品详情或提供更完整图片集的 profile 动作。目录核验于 2026-11-07：拼多多未在该服务目录中出现，本次不接入；TikTok、快手、Google Shopping 只有商品搜索、榜单、评价等能力，没有可用于当前单品链接流程的详情接口，因此不冒充来源支持。它们已有的生成目标选项继续保留。

服务端配置为 `POLARIS_EVERYINFRA_API_KEY` 和 `POLARIS_EVERYINFRA_PRODUCT_SOURCES_ENABLED=true`。新渠道仅在功能启用且已配置密钥时进入来源列表；密钥不进入浏览器或源码。前端来源选择读取 `/product-platforms`，目标平台选择补齐新渠道，Amazon 来源自动映射已有 `amazon-us` 生成目标。商品 ID 必须与上游返回身份一致；Amazon/Shopee 等按市场分别缓存。抖音需商城商品 ID，小红书需商城商品链接/ID，Shopee 需含店铺和商品 ID 的完整商品链接，非商品页拒绝。

用户速卖通商品 `3256807411229880` 的 EveryInfra 实测返回 6 张主图、13 张详情图、18 张 SKU 图。该商品先前的 CDN 429 已通过专用图片下载器修复：补全 User-Agent、Accept 和 Referer，优先协商系统支持的 WebP/JPEG/PNG/GIF，不改变图片 URL、像素尺寸或商品身份。下载器限制同进程两个并发，合并同一 URL 的同时请求，并用 64 MiB、10 分钟的有界缓存让预览和导入复用相同字节。HTTP 429/503 只在 Retry-After 不超过 5 秒时短暂等待并重试一次；不会立即重试较长限流，也不会无限循环。前端读取失败时保留图片位置并允许重新加载，不再因临时错误删除图片组中的条目。

2026-11-07 的完整候选镜像验证已逐张通过 37 次预览、37 张素材导入，并核对每张导入素材的 SHA-256 与预览字节一致；导入阶段未再次访问 CDN。验证使用隔离 SQLite 和临时素材存储，未调用商品查询或生成 API。修复发布后，正式页面也分别确认主图 6/6、详情图 13/13、SKU 图 18/18 全部解码显示。该结果针对用户提供的这件商品，不用返回字段数替代真实下载验证。

同日全渠道复查已补充天猫、得物和 Walmart 的真实样本。京东 EveryInfra 详情图需额外请求 `jd.description_images`，逐行校验商品 ID 后补全；Shopee 在 profile 图库之外额外请求一次 product_detail，校验商品 ID 后读取 variants 的 SKU 图；TEMU SKU 图读取 options 字段；Walmart profile 只有文字时改读 product_detail，保持同一商品 ID。补充接口失败时保留已有可用图片，不将卖家头像、评价、推荐商品或广告作为商品图。

小红书返回的 imageView2 转换参数指定 HEIF，原图无法通过当前预览/导入格式校验；下载时仅将同一 xhscdn 对象的 `/format/heif` 或 `/format/heic` 改为 `/format/webp`，保留路径及其余签名、查询参数。原始上游 URL 继续作为授权与导入幂等身份。其他电商图片也复用双并发、64 MiB、10 分钟缓存与同 URL 请求合并，连接超时仅重试一次，429/503 继续遵守短 Retry-After。前端对本次未返回的分组明确提示可手动补充。

本次隔离候选镜像验收覆盖 14 个渠道、20 组主/备样本：391 次分组图片预览全部通过，各样本内按 URL 去重后共 347 次图片导入校验全部通过（不是跨样本新增资产总数），SHA-256 与预览字节一致，所有导入均未额外请求 CDN。包括 1688 原主接口 5 主图 / 16 补充详情图 / 11 SKU、京东备用 8 / 11 / 8、Shopee 9 / 0 / 4、TEMU 2 / 0 / 2、小红书 5 / 12 / 0、Amazon 原服务 9 / 0 / 3、得物 6 / 0 / 0、Walmart 1 / 0 / 0。重叠 URL 在多分组显示，导入按原逻辑去重。

以上是样本实测，不保证每件商品都存在三个图片分组。Etsy 原样本详情返回 503，换用搜索得到的在售商品 4477536788 后 profile 成功取得并验证 11 张主图；其独立详情接口仍返回 503。eBay 原商品及搜索新得到的商品 206339597097 的详情接口均返回 503，没有将搜索缩略图冒充完整商品采集；它仍是待上游恢复的渠道。测试脚本为 `deploy/verify_all_commerce_images.py`：重放已记录的公开商品响应，只访问真实 CDN，使用临时 SQLite/素材目录，不带商品查询凭据、不挂载生产数据库、不触发生图。候选容器使用与线上 API 相同的网络环境完成验证。后端 175 项相关回归、前端 8 项相关测试、类型检查、lint 与构建通过。

EveryInfra 通过固定 HTTPS 地址 `/api/v1/social` 使用 Bearer 鉴权，不转发密钥至重定向地址，不自动循环重试。实际费用只记录响应中的已扣 USD 金额，不套用原供应商人民币单价；没有核验费用时保留空值。原上游与备用均失败时显示明确错误；轮询不重新付费查询，主动重试才会再次调用。商品 API 返回图片后依旧通过当前工作区的预览、勾选与素材导入权限完成后续流程。

该接入及同日图片修复已发布：基于当时正在运行的镜像，只覆盖采集相关模块、必要配置和一键复刻前端组件，未用本地完整应用替换其他并行发布。更新角色为 `replica-api`、`frontend`；其余八个应用角色的容器 ID 和镜像保持不变。图片修复保留了线上全部供应商环境配置。发布脚本保存服务器私有回滚配置，存在 API 采集/分析任务时禁止切换，健康检查失败自动恢复。正式页面已验证来源下拉框的 15 项渠道、新增目标选项，以及三类图片全部显示。未运行付费生图。 全渠道修复当前回滚目录为 `/etc/polaris/commerce-sources-all-20261107`，候选验收与发布证据在工作树 `outputs/all-channel-release-20261107/`。线上 9 个相关源码文件均已与验收工作树逐一核对 SHA-256。

本功能按网站供应商顺序配置：分析以 Tengli 为主、玩转为备用；生图以 Artflow 为主、Tengli 为备用。生图使用固定模型与画质，用户无需选择。两类备用路由独立，玩转凭证不会用于图片请求；传输结果不明时保留未知状态，避免自动重复生图扣费。图片生成沿用已有 `reference_remix` 任务、配额、用量、素材与任务记录。

新界面始终显式发送 `replication_method=exact|style`，不能只更换旧提示词的名称。省略该字段的旧客户端和历史 session 继续使用原有 `reference-visual-reverse-remix`，不会伪装成新 Skill；旧任务仍可恢复和下载。

## 一致性与资源边界

- `replica_documents` 保存商品缓存、分析进度、方案、确认指纹及子任务关联；只允许访问所属工作区。
- 商品导入仅接受本次接口返回的 CDN 图片，复用既有上传配额、图片校验和幂等机制。
- 新模式分析通过原始脚本验证模型 JSON；模型只观察与编写契约，不能自行改动状态、放宽门禁或计算图片哈希。语义失败必须重编方案后重新看图，不能要求把 FAIL 改写为 PASS。
- 已完成的分析结果在重试时复用。新的分析尝试使用独立标识，过期的排队尝试不能覆盖新结果。
- 新模式确认指纹绑定方式、Skill 哈希、原生快照哈希及方案。创建一个按顺序执行的整组任务，首项执行原生工作流，其余项发布已验收缓存；完整交付前不发布未接受的图片。
- 直接调用通用任务 API 不能绕过已确认 session。旧任务仍按原有逐图提交和恢复规则执行。
- 进程重启后未完成的分析会在超时后显示为可重试；生成任务沿用既有数据库 Outbox/Celery 恢复机制。
- JSON 原字节及私有图像对象的哈希快照保存在 session，API 与 Worker 无须共享临时目录。生图前先持久化调用令牌；结果未知的调用不自动重发，已返回的图像可在审计恢复时复用。
- 单图使用素材附件接口下载，不调用仅面向套图的 ZIP 接口。

## 发布边界

采用当前生产代码基线上的独立发布分支，保持其他对话的工作区和分支不变。

现有 `replica-api`、`replica-worker` 继续使用专属 `one_click_replica` 队列。本次只更新这两个角色及前端，不替换 dispatcher、Caddy 或详情服务，不执行数据库迁移。当前代理已覆盖嵌套 replica 路径。

详情 API、详情 Worker 及其模型、环境、任务与状态不属于本次替换范围。发布前检查当前容器与配置摘要，完成备份/恢复预检；变更时校验基线，避免覆盖同时发生的发布。

`deploy/release_replica_native.py` 在服务器私有目录保存当前配置、九角色基线和数据库备份，逐阶段检查原服务和代理不变，只操作三种角色。凭据不导出；构建明确包含完整 Skill 源与清单。回滚前必须排空复刻任务及分析，防止旧 Worker 接手新模式；回滚保留数据及对象。

本地结构测试不能证明视觉成功。真实验收使用用户明确授权的现有香水商品/参考图与供应商，保存原生审计和最终图；一比一最终样本在补丁后重新生成并通过新鲜逐项审计。风格的八类机制阈值均为 0.8，产品身份、事实和污染问题为硬失败。验收数据是单幅香水场景样本，不代表所有商品和长详情均已真实验证。
