# Video studio gray release

The video business API has a single server-side verified-email gate for `1474953130@qq.com`. This release does not widen it or replace production authentication. It uses a dedicated `video-api` service and durable `polaris-production_video_studio_data` volume; existing image/crawl/replica workers remain on their observed images.

1. Require a clean pinned source commit, passing CI, and explicit commit/merge/deploy authorization. Record current container IDs/images, schema revision, current Caddy hash and networks. This release expects schema `20261030_0034` before additive migrations 0035–0039.
2. Build the backend and frontend from the exact reviewed tree with approved base-image digests. Record immutable image IDs. No real env files, user recordings, credentials, local SQLite databases, or cached audio belong in source archives.
3. Run `backup_restore.py --revision <full-source-sha> --image <backend-image-id>` on the production host. This takes a DB snapshot followed by an immutable S3 object archive, restores both into a new internal network and new volumes, checks live-asset hashes, rehearses migrations, checks API readiness, and completes a zero-cost mock job. It never stops or restores into production containers. Preserve the paired archive and checksummed manifest.
4. Pass only the allowlisted video runtime settings through stdin to `prepare.py --revision <sha> --backend-image <id> --frontend-image <id> --baseline <sanitized-audit-json>`. Keep all generated files server-local and mode 0600. It copies inspected runtime env/command fields, security settings, networks and TLS volumes. Original Caddy content including API/payment entries is retained. Existing API aliases must never be assigned to the new video service.
5. Create and initialize the dedicated media volume for UID/GID 10001. Validate both private Compose documents and Caddy with the current immutable Caddy image. Use a confirmed backup/restore manifest before `alembic upgrade head` in the new image against production. Never downgrade these append-only history/consent tables.
6. Copy the existing 327 fixed previews and the user's ready cloned voice/preview into private media storage, verifying hashes. Import only the clone business record under the existing target user and their existing owner workspace; do not rewrite users, auth subjects or membership. Clone enrollment and preview synthesis must not be repeated as a deployment step.
7. Start `video-api` without changing dependencies or exposing a host port. Require healthy status. After main is merged with the reviewed tree, update only the frontend and Caddy using the prepared overlay with `--no-deps --no-build --pull never`. Verify other container IDs/images are unchanged.
8. Run main health checks; check video APIs reject anonymous access, authenticate the gray user normally, and confirm the existing voice and cached preview appear online. Verify the public main, API transit, and payment routes still respond. Do not trigger paid video generation as an availability probe.

Application rollback uses `rollback.compose.private.json` for the previous frontend and Caddy, stops only the new video service if needed, and retains the new tables and media. Keep all credentials, paired backups and media outside Git and outside publicly served directories. `prepare.py` does not itself apply Compose or run migrations.
