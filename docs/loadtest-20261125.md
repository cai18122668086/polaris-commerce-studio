## 瓶颈

1. **主 api 单进程、0.5 CPU（基线）**：50 VU 时 api 的 CPU 一直顶在上限（52.9%，上限是 0.5 核），所有读接口一起变慢。p95 从 25 VU 时的 0.1–0.6 s 涨到 6–15 s，吞吐反而下降：稳态请求数 4104，而按 25 VU 线性推算应约 6200。连接池只有 3+2，请求在池里排队超过 5 s，就出现 `QueuePool limit ... timeout 5.00`，并变成 5xx。改后（3 个 worker、池 8+8）这一点消失；但 api 仍然吃满 1.0 CPU 上限（102%），内存 745/768 MiB。正式值是 1.5 CPU / 1 GiB。**50 VU 已经接近这个 api 的上限**：3 个 worker 各约 230–250 MiB，1 GiB 的余量不大，建议上线后观察 api 的 RSS，或给到 1.25 GiB。
2. **出图吞吐**：default 队列只有 6 个并发，每张图 20–40 s，理论上限约 12 张/分钟。50 VU 时 default 队列峰值是 54（基线）和 28（改后），主图任务从提交到完成 p50 = 90 s（基线）和 73 s（改后），10 VU 时是 36 s。这是 worker 并发和上游时延决定的，C 的改动没有动它。若要更快，需要加 worker 并发或加副本，并同时核对上游并发配额（IMAGE_GLOBAL_CONCURRENCY=40）。
3. **复刻队列**：replica-worker 并发只有 2。改后 api 不再是瓶颈，任务都进了队列，one_click_replica 峰值 93，复刻任务 p50 104 s、p95 152 s；稳态 5 分钟里有 15 个复刻没跑完（基线是 11 个规划没完成）。50 人同时用复刻时需要把并发调到 4 以上。2026-10-23 的容量文档已经建议过 4。
4. **detail-worker 内存**：6 个 prefork 子进程空闲时就占约 450 MiB，有负载时会顶到 staging 的 896 MiB 上限，被 cgroup 杀掉子进程（WorkerLostError，signal 9），celery 会重启子进程，任务大多仍能完成（改后 27/28）。正式站上限是 2 GiB，空闲 493 MiB，这次没有在 2 GiB 下测，**是否会 OOM 未验证**。建议在正式的 detail-worker 上观察峰值 RSS，或把 `--max-memory-per-child` 设到 280 MB 左右。
5. **登录**：SuperTokens 0.25 CPU 时，50 人集中登录的 p95 是 16–17 s；0.5 CPU（正式值）时，改后 p95 1.17 s，基线 9.5 s（基线的主要原因是 api 被打满）。正式站不要把 SuperTokens 降到 0.5 CPU 以下。
6. 改后没有出现 IntegrityError、Traceback（api）或连接池超时。postgres 峰值 32% CPU（0.35 核），不是瓶颈。

## 视频

## 安全阀事件

所有阶段都在 guard 下运行。guard 一共叫停 7 次，**全部是主机或其他线程造成的**：

- 5 次是 1 分钟负载大于 6，当时其他线程正在跑 pytest。
- 2 次是其他线程的 CI 临时数据库容器自身 CPU 打满：`polaris-ci-pg-tmp` 和 `polaris-g-pg-tmp`。之后把 `polaris-ci-*` 排除出了 guard 的检查范围（不属于正式站）；`polaris-g-pg-tmp` 仍按正式容器对待。
- 被叫停的阶段都在主机安静后重跑完成，报告里用的都是没被叫停的那一次。
- 全程正式容器 RestartCount 都是 0，StartedAt 没有变化。正式容器 CPU 超过上限 85% 的单次告警有若干次，都是正式站自己的任务（detail-worker、worker），没有出现连续 3 次。
- guard 自测：负载、内存、CPU、重启四种条件都实际杀掉了测试进程，记录在 `loadtest/guard-selftest.log`。

## 备份与恢复演练

- **脚本**：`deploy/backup/polaris-backup.sh`，用 docker exec 调用容器自带的 pg_dump，自定义格式，压缩级别 6。
  - pg_dump 和逐表行数共用同一个 REPEATABLE READ 快照（`pg_export_snapshot` + `--snapshot`），所以在线库边写边备份时，行数也和 dump 一致。
  - 先用 `pg_restore -l` 校验 dump 可读，再生成 sha256。
  - MinIO 用 `mc mirror --overwrite --preserve` 做增量镜像，凭据通过 env 文件传入，不出现在命令行和日志里。
  - 数据库备份按 `--keep-days` 清理，带 flock 防止重入。
- **systemd 示例**：`polaris-backup.service.example` / `.timer.example`，北京时间每天 04:20 执行，带 Nice、idle IO、CPUQuota 50%、MemoryMax 1G。没有装到主机上。
- **恢复演练**：`deploy/backup/polaris-restore-drill.sh`，只在 staging 上跑过。流程是：校验 sha256 → 恢复到临时库 `drill_*` → 逐表比对行数 → 比对 MinIO 对象数，并随机抽 5 个对象比对 sha256 → 删除临时库。脚本拒绝在名字含 production 的容器里执行。

| 演练 | 数据规模 | 结果 |
| --- | --- | --- |
| 1（压测前） | 130 张表，dump 564 KB；36 个对象 | 通过，0 处不一致 |
| 2（第一轮基线后） | 130 张表，11 302 行，1.4 MB；575 个对象 / 399 MB | 通过，0 处不一致 |
| 3（全部压测后，旧版脚本） | 130 张表，dump 3.4 MB；1832 个对象 / 1.3 GB | **不通过**，4 张表行数比 dump 多 2–5 行：旧版在 dump 之后才数行数，期间 worker 还在写。据此改成了共用快照 |
| 4（新脚本） | 130 张表，dump 3.4 MB；1832 个对象 | 通过，0 处不一致 |
| 5（新脚本，备份期间另开进程每秒写入几十行） | 131 张表 | 通过，0 处不一致；快照里该表 21 行，写入进程结束时 400 行 |

耗时：dump 3–16 s，恢复 5–7 s，mirror 1.3 GB 用了 47 s。正式站数据量更大，实际耗时需要另测。
